# Hezhou Engine 项目计划（2026-11）

> 状态：草案，待评审  
> 基线版本：`v0.1.0`（2026-10-18 发布）  
> 文档目标：把“差距盘点”转成可执行、可验收、可排期的工程计划  
> 建议策略：**垂直切片优先（Vertical Slice First）**，先证明“能用 Hezhou 做一个完整小游戏”，再补生产级工具和平台。

---

## 1. 执行摘要

Hezhou 已经具备一个可运行的引擎/编辑器垂直切片：

- Rust 引擎 + C# Mono 脚本 + Vulkan 渲染
- 自研 Widget UI、Inspector、Dock、命令面板、Gizmo、撤销重做
- C# 热重载
- ECS、基础物理、基础动画、资源库、工程保存
- MSI / MSIX / DEB 安装包
- AI/MCP 场景操作接口

但距离“可用于完整游戏项目”的主要缺口是：

1. **没有音频**
2. **没有完整资产管线**（只有 OBJ，缺少 glTF/骨骼/导入设置/Prefab）
3. **没有骨骼动画**
4. **没有阴影、PBR、完整后处理**
5. **没有游戏 Player 导出**
6. **编辑器缺少动画/材质/构建/Profiler 等生产工具**
7. **平台和网络覆盖不足**
8. **RHI/ECS 等底层仍有架构债**

因此本计划不追求“一次做成 Unity”，而是分三个可交付阶段：

| 阶段 | 目标 | 版本 | 核心判断标准 |
|---|---|---|---|
| Phase 0 | 立项与基线 | — | 目标样例游戏、性能基线、技术选型确定 |
| Phase 1 | 可玩的垂直切片 | `0.2.0` | 一个 3～5 分钟小游戏能从编辑器导出并独立运行 |
| Phase 2 | 可用的编辑器 | `0.3.0` | 能支撑一个小团队做完整项目，编辑器工具链基本闭环 |
| Phase 3 | 可扩展的引擎 | `0.4.0 / 1.0` | 平台、网络、生态和稳定性达到对外发布标准 |

## 2. 当前基线

### 2.1 已有能力

- **渲染**：Vulkan、天空渐变、方向光 Blinn-Phong、纹理、选中 outline、FXAA、实验性 compute ray tracing
- **UI**：18 种 Widget、双主题、SVG 图标、Dock、命令面板、Widget Gallery
- **编辑器**：项目树、Inspector、资产浏览、Console、Gizmo、多选、撤销/重做、拖拽层级
- **脚本**：C# / Mono JIT、热重载、`[Expose]` 属性反射
- **场景**：Transform、层级、方向光、Renderable、ScriptBinding、AnimationPlayer
- **物理**：自研 AABB 碰撞、简单刚体、射线、CharacterController
- **资源**：OBJ、PNG/BMP、程序化纹理、工程 JSON
- **DFX**：日志、崩溃捕获、Trace、Trace Viewer
- **发布**：MSI、MSIX、DEB、内置 Mono 运行时、无终端启动器
- **AI**：18 个 MCP 工具

### 2.2 关键缺口

- 渲染：无 Shadow Map、无 PBR、无 SSAO/Bloom/Tonemap/GI/IBL
- 资产：无 glTF/FBX、无导入设置、无 Meta/UUID、无 cooker、无 Prefab
- 动画：无骨骼/蒙皮/Blend Tree/状态机/根运动
- 音频：无 audio crate
- 构建：只能打包编辑器，不能导出游戏
- 工具：无动画编辑器、材质编辑器、构建设置、集成 Profiler、脚本调试
- 平台：Windows/Linux；HarmonyOS 实验性；无 macOS/Android/iOS/Web/主机
- 网络：无
- 2D/地形/粒子/寻路：无
- 架构：RHI command buffer 仍有 TODO、部分 `static mut`、ECS 不是 archetype/并行调度
- 质量：CI 缺 GPU 渲染回归和性能门禁

### 2.3 与主流引擎的差距摘要

| 维度 | Hezhou 当前 | Unity / Unreal / Godot 基线 | 计划对应 |
|---|---|---|---|
| 渲染 | Blinn-Phong + FXAA；实验性 RT | PBR、阴影、后处理、GI、LOD | Phase 1 |
| 资产 | OBJ + PNG/BMP；无 cooker | glTF/FBX、导入设置、Prefab、Addressables | Phase 1 |
| 动画 | Transform 关键帧 | 骨骼、Blend Tree、状态机、IK | Phase 1 |
| 音频 | 无 | 混音、空间音频、流式 | Phase 1 |
| 物理 | 自研 AABB；无关节/CCD | PhysX/Jolt/Chaos 级 | Phase 2 |
| 构建 | 只打包编辑器 | Player 导出 + 资源烘焙 | Phase 1 |
| 编辑器 | 自研面板/撤销/Gizmo | 动画/材质/构建/Profiler/调试器 | Phase 2 |
| 平台 | Windows/Linux（Harmony 实验） | macOS/移动/Web/主机 | Phase 3 |
| 网络/生态 | 无 | 多人、插件、商店、文档 | Phase 3 |

> 详细对比见本次差距盘点；本计划只保留与排期直接相关的摘要。

## 3. 目标、范围与非目标

### 3.1 产品目标

**一句话目标：让独立开发者或 2～5 人小团队，能用 Hezhou 在 1～2 个月内做出并发布一个小型 3D 游戏。**

### 3.2 工程目标

- 建立“编辑器 → 资源烘焙 → Player 导出 → 安装包/压缩包”的完整发布链路
- 建立可测试的渲染/资产/动画/音频基础设施
- 保持 Hezhou 的差异化：轻量、Rust、C# 热重载、自研 UI、AI/MCP
- 每个阶段必须有可运行 Demo，不允许“只做底层没有产出”

### 3.3 0.2.0 明确不做（Non-goals）

以下内容**不进入 0.2.0**，避免范围失控：

- 多人网络
- 移动端/主机/Web
- 地形系统、NavMesh、寻路
- 大型粒子系统
- Shader Graph / 材质图
- 资源商店 / 插件市场
- 多窗口编辑器 / 协同编辑
- 完整全局光照 / 生产级路径追踪
- 主机平台认证

> 0.3 和 0.4 再按目标游戏类型逐步解锁。

## 4. 总体里程碑

按 **3 名全职工程师 + 0.5 名设计/QA** 估算，节假日未扣除。人数变化时按“人周”重排。

| 阶段 | 时间窗口 | 版本 | 里程碑 |
|---|---|---|---|
| Phase 0 | 2026-11-02 ～ 2026-11-13 | — | 立项完成：样例游戏、基线、ADR、CI 计划 |
| Phase 1 | 2026-11-16 ～ 2027-02-07 | `0.2.0` | 可玩垂直切片 + Player 导出 |
| Phase 2 | 2027-02-08 ～ 2027-05-16 | `0.3.0` | 编辑器工具链闭环 + 物理/动画增强 |
| Phase 3 | 2027-05-17 ～ 2027-09-05 | `0.4.0 / 1.0` | 平台、网络、生态、稳定性 |

### 4.1 关键路径

```text
目标游戏定义
   ↓
资产管线（glTF + 资产数据库）
   ↓
骨骼动画 + 渲染（PBR/阴影）
   ↓
音频 + 玩法组件
   ↓
Player 导出 + 样例游戏
   ↓
编辑器工具链（Prefab/动画/构建/Profiler）
   ↓
平台与生态
```

**关键路径上的任何一项延期，0.2.0 都会延期。** 其中资产管线、骨骼动画、Player 导出是最高风险项。

## Phase 1：可玩的垂直切片（12 周，`0.2.0`）

### 目标

做出一个 **3～5 分钟可玩**的 3D 小游戏，并且：

- 在 Hezhou 编辑器里编辑
- 能导出独立 Player
- 在干净的 Windows 机器上运行（无需安装 Mono）
- 在 Linux 上至少能运行压缩包版本
- 有声音、有动画、有 UI、有关卡流程

### 1.1 音频子系统（2～3 人周）

**新增 `engine/audio`**

- 播放/暂停/停止/循环
- 音量、静音、总线
- 2D 音效 + 3D 衰减
- 流式/预加载两种模式
- C# API + 编辑器音频预览
- 打包时自动收集音频资源

**验收**

- [ ] 样例游戏有背景音乐 + 至少 5 个音效
- [ ] 3D 音效随相机距离衰减
- [ ] 无音频设备时不崩溃
- [ ] 音频资源随 Player 导出

**建议技术选型**：`kira`（混音/空间音频）或 `cpal + 自研混音`；Phase 0 做 2 天 spike 后定 ADR。

### 1.2 资产管线 v2（4～5 人周）

**新增 `engine/asset`**

- 资产数据库：UUID、路径、类型、依赖、导入设置
- `.meta` 文件
- glTF/GLB 导入：Mesh、Material、Texture、Skeleton、Animation
- 纹理导入：PNG/JPEG，sRGB/线性、mipmap、压缩策略
- 资源引用从“字符串路径”升级为“AssetId”
- 资产 cooker：把编辑器资产烘焙成 Player 格式
- 资产热重载（编辑器内）

**验收**

- [ ] 导入一个带骨骼和动画的 glTF 角色
- [ ] 修改纹理后编辑器可热重载
- [ ] 工程移动目录后引用不丢失
- [ ] Player 包只包含被引用的资源

### 1.3 骨骼动画（4～5 人周）

- glTF skin/joint 导入
- GPU 蒙皮（顶点着色器）
- AnimationClip 播放/循环/速度
- 简单 AnimationStateMachine（Idle/Walk/Run/Jump）
- 动画事件（脚步、攻击判定）
- 根运动（可选，若样例游戏需要）

**验收**

- [ ] 角色可播放 Idle/Walk/Run
- [ ] 状态切换无明显跳变
- [ ] 骨骼动画在 Player 中正常
- [ ] 动画资源随包导出

### 1.4 渲染：PBR + 阴影 + 后处理（4～5 人周）

- PBR 材质：albedo / metallic / roughness / normal / AO
- 方向光 Shadow Map（至少 1 级，建议 2～3 级 cascade）
- Tone mapping + Gamma
- Bloom（可选，若样例游戏需要）
- 保留 FXAA
- 渲染管线可配置（低/中/高）

**验收**

- [ ] 基准场景有可见阴影
- [ ] 金属/粗糙度视觉正确
- [ ] 1080p 下样例场景达到 60 FPS（目标硬件见 §8）
- [ ] 低配模式可关闭阴影/Bloom

### 1.5 Player 导出（4～5 人周）

**新增 `engine/player`（或 `examples/src/hezhou_player.rs` + 构建器）**

- `hezhou build` 或编辑器“导出游戏”
- 输出：exe/可执行文件 + 烘焙资产 + 预编译 C# 程序集 + 运行时
- Windows：无终端、无 Mono 依赖、可打包 zip/安装包
- Linux：可执行 + 资产目录/压缩包
- 启动参数：窗口模式、分辨率、日志路径
- 构建配置：启动场景、窗口标题/图标、版本号

**验收**

- [ ] 干净 Windows 机器双击即可运行样例游戏
- [ ] 不要求用户安装 Mono
- [ ] 不弹出终端
- [ ] 构建产物可重复、带版本号
- [ ] 构建日志和错误信息可读

### 1.6 Prefab 与场景工作流（2～3 人周）

- Prefab 资产：保存实体子树
- 实例化、覆盖字段、Prefab 嵌套（基础）
- 场景切换/加载
- 启动场景配置

**验收**

- [ ] 角色/敌人/道具以 Prefab 形式复用
- [ ] 修改 Prefab 后场景实例可更新
- [ ] 样例游戏至少 2 个场景可切换

### 1.7 样例游戏 + 集成测试（3～4 人周）

- 一个完整小游戏（题材待 Phase 0 确定）
- 核心循环、失败/胜利、UI、音效、存档（可选）
- 性能优化、内存检查、30 分钟稳定性测试
- 在 Windows/Linux 各跑一遍完整流程

### Phase 1 退出条件（0.2.0 Definition of Done）

- [ ] 样例游戏可从编辑器导出并独立运行
- [ ] Windows Player 不依赖 Mono、无终端
- [ ] 音频、骨骼动画、阴影/PBR、Prefab 至少各有一个可演示场景
- [ ] 30 分钟连续运行无崩溃、无明显内存增长
- [ ] CI 全绿：Rust、C#、资产、动画、打包
- [ ] Release 包含 Editor 安装包 + Sample Game Player
- [ ] 已知问题清单和 0.3 待办明确

## Phase 2：可用的编辑器（14 周，`0.3.0`）

### 目标

让一个小团队能持续开发项目，而不是只能做 demo。

### 2.1 物理升级（4 人周）

- 接入 `rapier3d`（推荐）或完善自研物理
- 碰撞层/掩码、触发器
- 关节/弹簧/约束
- 连续碰撞检测（CCD）
- 胶囊角色控制器完善
- 物理调试可视化

**验收**

- [ ] 样例游戏角色可稳定上下坡、跳跃、推箱子
- [ ] 触发区可驱动游戏逻辑
- [ ] 100 个动态刚体场景稳定 60 FPS

### 2.2 编辑器工具链（8 人周）

- 动画时间轴/动画预览
- 材质编辑器（至少 PBR 参数 + 贴图槽）
- 构建设置面板（场景、图标、分辨率、包名）
- 资产导入设置面板
- Prefab 编辑模式
- 场景视图多标签（可选）
- 更完整的 Dock 拖拽停靠
- 控制台过滤/搜索/源码跳转完善

### 2.3 Profiler 与调试（4 人周）

- 集成 CPU 帧 Profiler（复用 DFX Trace）
- 内存统计
- Draw call / 三角形 / 显存统计
- 编辑器内性能面板
- C# 脚本异常面板
- 脚本调试（至少异常堆栈 + 行号；断点调试可延后）

### 2.4 MCP/AI 工具补全（2 人周）

- `run_script` 真正执行 C#（当前 `not implemented`）
- 截图/视觉反馈工具
- 场景操作批量事务/撤销
- MCP 工具权限与安全边界

### 2.5 C# API 与文档（3 人周）

- 稳定的 C# API 程序集
- API 参考文档
- 入门教程：创建工程 → 场景 → 脚本 → 构建
- 示例项目 2～3 个

### 2.6 质量与性能（3 人周）

- 增加资产/动画/物理/构建测试
- 渲染 golden image 测试（至少 3 个固定场景）
- 性能门禁：帧时间、启动时间、包体
- 长时间运行/内存泄漏测试

### Phase 2 退出条件

- [ ] 可从零创建一个工程并完成“角色 + 关卡 + UI + 音效 + 导出”
- [ ] 动画/材质/构建设置可在编辑器内完成
- [ ] Profiler 能定位 CPU/GPU/内存瓶颈
- [ ] 至少 2 个示例项目
- [ ] API 文档和入门教程可用

## Phase 3：可扩展的引擎（16 周，`0.4.0 / 1.0`）

### 目标

从“能用”走向“可对外发布、可扩展”。

- 传输层抽象
- 房间/连接管理
- 状态同步/RPC
- 服务器权威基础
- 一个多人 demo

> 若目标游戏不是多人，此项可整体后移。

### 3.3 内容生产能力（10 人周，按目标裁剪）

- 2D 精灵/Tilemap（若做 2D 游戏）
- 粒子系统
- 地形
- NavMesh/寻路
- 更完整的动画状态机/Blend Tree

### 3.4 插件与生态（5 人周）

- 编辑器插件 API
- 项目模板
- 包管理器（最小可用）
- 示例/教程/社区文档

### 3.5 稳定性与发布（4 人周）

- 崩溃报告/诊断包
- 自动更新（可选）
- 安装包签名/公证
- 1.0 发布 checklist

### Phase 3 退出条件

- [ ] 至少 2 个目标平台可发布
- [ ] 有一个非团队开发者按文档完成 demo
- [ ] 插件/模板机制可用
- [ ] 1.0 稳定性/性能/文档达到发布标准

- 音频依赖 Player 音频资源打包

- PBR/阴影依赖资产材质和渲染管线
- Player 导出依赖资产 cooker + 预编译 C#
- Prefab 依赖资产数据库
- 样例游戏依赖以上全部

## 7. 技术决策（ADR 清单）

| ADR | 决策 | 备选 | 截止 |
|---|---|---|---|
| ADR-001 | 音频后端：kira / cpal + 自研混音 | FMOD/Wwise（商业，暂不选） | Phase 0 |
| ADR-002 | 物理：接入 rapier3d / 自研 AABB 扩展 | PhysX（C++ 集成重） | Phase 0 |
| ADR-003 | 资产格式：glTF-first + Meta/UUID | 自研格式 / FBX SDK | Phase 0 |
| ADR-004 | Player：独立 `hezhou-player` + 资产 cooker | 编辑器内置运行 / 导出脚本 | Phase 0 |
| ADR-005 | 渲染：Forward+ PBR + Shadow Map | Deferred / 纯 RT | Phase 0 |
| ADR-006 | C#：编辑器 JIT / Player 预编译程序集 | 全 JIT / NativeAOT | Phase 0 |
| ADR-007 | ECS：保持现有 World / 引入 archetype | Bevy ECS / 自研 | Phase 2 |

**规则**：ADR 必须有背景、决策、备选、后果、验证方式；未评审不得开工。

## 8. 质量、性能与 CI

### 8.1 质量门禁

每个 PR 必须：

- `cargo fmt --check`
- `cargo clippy`（关键 crate）
- Rust 单测/FFI 契约测试
- C# 编译
- 资产/动画/物理新增测试
- 打包脚本至少本地 dry-run

每个里程碑必须：

- 完整 E2E：创建工程 → 编辑 → 导出 → 运行
- Windows/Linux 双平台冒烟
- 30 分钟稳定性测试
- 性能数据对比基线

### 8.2 性能预算（0.2.0）

| 指标 | 目标 |
|---|---|
| 编辑器启动 | < 5 秒 |
| Player 启动 | < 5 秒 |
| 样例场景 1080p | 60 FPS（目标硬件：集成显卡/低端独显） |
| 样例场景 Draw Call | < 500 |
| Player 包体（不含安装器） | < 200 MB |
| 内存增长（30 分钟） | < 10% |
| 崩溃率（测试场景） | 0 |

### 8.3 CI 扩展

现有作业继续保留：

- `rust-tests`
- `csharp-build`
- `package-windows`（MSI + MSIX）
- `package-linux`（DEB）
- `publish-release`

新增：

- `asset-tests`：导入/依赖/ cooker
- `animation-tests`：骨骼/状态机
- `audio-tests`：无声卡环境
- `player-build`：导出 Player 并冒烟运行
- `rendering-golden`（可选，自托管 GPU runner）：固定场景截图对比
- `performance`（可选，夜间）：帧时间/包体回归

## 10. 风险与对策

| 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|
| 资产管线范围失控 | 高 | 高 | glTF-first，先支持样例游戏用到的子集；FBX/其他格式后置 |
| 骨骼动画/蒙皮复杂度超预期 | 中 | 高 | 先做单骨骼链 + 1 个角色，Blend Tree 后置；Phase 0 spike |
| Player 导出依赖 Mono/运行库 | 中 | 高 | Player 预编译 C#，Windows 打包运行库；干净机器验收 |
| 渲染重写导致回归 | 中 | 高 | 保留现有 raster 路径，PBR/阴影作为可切换管线；golden test |
| GPU 差异/CI 无 GPU | 高 | 中 | 本地 GPU 冒烟 + 自托管 runner（可选）；软件/低配模式 |
| 范围蔓延 | 高 | 高 | 0.2.0 Non-goals 写死；变更需评审并替换等量任务 |
| 人员不足 | 中 | 高 | 按人周重排；优先保证 Player 闭环，工具后置 |
| MCP/AI 安全 | 低 | 中 | 工具权限分级、危险操作确认、审计日志 |
| MSIX 自签名证书体验 | 中 | 低 | 文档 + `.cer`；长期考虑代码签名证书 |
| 第三方库许可/维护 | 低 | 中 | Phase 0 做依赖审查；锁定版本 |
