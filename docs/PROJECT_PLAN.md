## 1. 执行摘要

Hezhou 已经具备一个可运行的引擎/编辑器垂直切片：

- Rust 引擎 + C# Mono 脚本 + Vulkan 渲染
- 自研 Widget UI、Inspector、Dock、命令面板、Gizmo、撤销重做
- C# 热重载
- ECS、基础物理、基础动画、资源库、工程保存
- MSI / MSIX / DEB 安装包
- AI/MCP 场景操作接口

但距离“可用于完整游戏项目”的主要缺口是：

1. **没有音频**
2. **没有完整资产管线**（只有 OBJ，缺少 glTF/骨骼/导入设置/Prefab）
3. **没有骨骼动画**
4. **没有阴影、PBR、完整后处理**
5. **没有游戏 Player 导出**
6. **编辑器缺少动画/材质/构建/Profiler 等生产工具**
7. **平台和网络覆盖不足**
8. **RHI/ECS 等底层仍有架构债**

因此本计划不追求“一次做成 Unity”，而是分三个可交付阶段：

| 阶段 | 目标 | 版本 | 核心判断标准 |
|---|---|---|---|
| Phase 0 | 立项与基线 | — | 能力清单、演示工程、性能基线、技术选型确定 |
| Phase 1 | 引擎能力垂直切片 | `0.2.0` | 3D 动作所需核心能力可组合，并能导出双平台 Player |
| Phase 2 | 可用的编辑器 | `0.3.0` | 能支撑一个小团队做完整项目，编辑器工具链基本闭环 |
| Phase 3 | 可扩展的引擎 | `0.4.0 / 1.0` | 平台、网络、生态和稳定性达到对外发布标准 |

---

### 引擎能力与示例内容的边界

Hezhou 不把某一款动作游戏的规则写死在引擎里，而是提供可复用的能力。0.2 必须交付以下**引擎能力**：

| 能力域 | 0.2 引擎能力 |
|---|---|
| 角色控制 | `CharacterMotor`、第三人称跟随相机、锁定目标（LockOn）组件 |
| 战斗 | 攻击定义/连招图、命中盒（Hitbox）、伤害/生命值、闪避、格挡、受击反馈 |
| 动画 | 骨骼/蒙皮、AnimationStateMachine、动画事件、动作过渡 |
| 物理 | 胶囊角色扫掠、静态碰撞、碰撞层/触发器、射线/命中查询 |
| 渲染 | PBR、Shadow Map、Tonemap、可配置质量档 |
| 音频 | 播放/总线/2D/3D 衰减/流式 |
| 资产 | glTF 导入、AssetId/UUID、Meta、cooker |
| 构建 | Windows/Linux Player 导出、预编译 C#、资产烘焙 |
| 编辑器 | 组件/属性编辑、Prefab、动画预览、构建设置 |

**示例工程只做组合验证**：它使用上述能力搭一个 3～5 分钟的演示关卡，用来说明 API 可用、手感可调、可导出；示例中的关卡/敌人/数值不属于引擎核心，也不会硬编码进引擎。

### 决策记录（已确认）

| 编号 | 决策 | 对计划的影响 |
|---|---|---|
| D1 | 目标类型为 **3D 动作游戏**，但 Hezhou 做的是**引擎能力**，不是具体游戏 | 角色控制、第三人称相机、锁定、连招/命中/受击等作为通用组件提供；演示工程只负责组合验证 |
| D2 | **骨骼动画进入 0.2** | glTF 骨骼/蒙皮、动作状态机、6 个基础动作成为 0.2 必交付项 |
| D3 | **物理自研，不接 rapier** | 0.2 做动作游戏需要的胶囊角色、静态碰撞、命中盒、触发器；完整刚体/关节/CCD 延到 0.3 |
| D4 | **Windows + Linux Player 同步交付** | Player 构建、资产路径、输入、Vulkan、CI 双平台矩阵从 0.2 开始 |
| D5 | **AI 并行生成，人数不作为主要约束** | 排期按“集成/评审/QA 带宽”而非人头计算；任务必须拆分写作用域并通过 CI |
| D6 | 音频后端采用 **cpal + 自研混音**，OGG 用 lewton | 不选 kira；保留 NullBackend 用于无声卡/CI |
| D7 | animation 与 gameplay 互不依赖，由 **engine/integration** 适配 | 两者只提供能力，不互相硬绑定 |

## 2. 当前基线

### 2.1 已有能力

- **渲染**：Vulkan、天空渐变、方向光 Blinn-Phong、纹理、选中 outline、FXAA、实验性 compute ray tracing
- **UI**：18 种 Widget、双主题、SVG 图标、Dock、命令面板、Widget Gallery
- **编辑器**：项目树、Inspector、资产浏览、Console、Gizmo、多选、撤销/重做、拖拽层级
- **脚本**：C# / Mono JIT、热重载、`[Expose]` 属性反射
- **场景**：Transform、层级、方向光、Renderable、ScriptBinding、AnimationPlayer
- **物理**：自研 AABB 碰撞、简单刚体、射线、CharacterController
- **资源**：OBJ、PNG/BMP、程序化纹理、工程 JSON
- **DFX**：日志、崩溃捕获、Trace、Trace Viewer
- **发布**：MSI、MSIX、DEB、内置 Mono 运行时、无终端启动器
- **AI**：18 个 MCP 工具

### 2.2 关键缺口

- 渲染：无 Shadow Map、无 PBR、无 SSAO/Bloom/Tonemap/GI/IBL
- 资产：无 glTF/FBX、无导入设置、无 Meta/UUID、无 cooker、无 Prefab
- 动画：无骨骼/蒙皮/Blend Tree/状态机/根运动
- 音频：无 audio crate
- 构建：只能打包编辑器，不能导出游戏
- 工具：无动画编辑器、材质编辑器、构建设置、集成 Profiler、脚本调试
- 平台：Windows/Linux；HarmonyOS 实验性；无 macOS/Android/iOS/Web/主机
- 网络：无
- 2D/地形/粒子/寻路：无
- 架构：RHI command buffer 仍有 TODO、部分 `static mut`、ECS 不是 archetype/并行调度
- 质量：CI 缺 GPU 渲染回归和性能门禁

### 2.3 与主流引擎的差距摘要

| 维度 | Hezhou 当前 | Unity / Unreal / Godot 基线 | 计划对应 |
|---|---|---|---|
| 渲染 | Blinn-Phong + FXAA；实验性 RT | PBR、阴影、后处理、GI、LOD | Phase 1 |
| 资产 | OBJ + PNG/BMP；无 cooker | glTF/FBX、导入设置、Prefab、Addressables | Phase 1 |
| 动画 | Transform 关键帧 | 骨骼、Blend Tree、状态机、IK | Phase 1 |
| 音频 | 无 | 混音、空间音频、流式 | Phase 1 |
| 物理 | 自研 AABB；无关节/CCD | PhysX/Jolt/Chaos 级 | Phase 2 |
| 构建 | 只打包编辑器 | Player 导出 + 资源烘焙 | Phase 1 |
| 编辑器 | 自研面板/撤销/Gizmo | 动画/材质/构建/Profiler/调试器 | Phase 2 |
| 平台 | Windows/Linux（Harmony 实验） | macOS/移动/Web/主机 | Phase 3 |
| 网络/生态 | 无 | 多人、插件、商店、文档 | Phase 3 |

> 详细对比见本次差距盘点；本计划只保留与排期直接相关的摘要。

## 3. 目标、范围与非目标

### 3.1 产品目标

**一句话目标：让独立开发者或 2～5 人小团队，能用 Hezhou 在约 3～4 个月内做出并发布一个小型 3D 动作游戏；首个内部可玩版本约 8～10 周，完整 0.2 验收约 12 周。**

### 3.2 工程目标

- 建立“编辑器 → 资源烘焙 → Player 导出 → 安装包/压缩包”的完整发布链路
- 建立可测试的渲染/资产/动画/音频基础设施
- 保持 Hezhou 的差异化：轻量、Rust、C# 热重载、自研 UI、AI/MCP
- 每个阶段必须有可运行 Demo，不允许“只做底层没有产出”

### 3.3 0.2.0 明确不做（Non-goals）

以下内容**不进入 0.2.0**，避免范围失控：

- 多人网络
- 移动端/主机/Web
- 地形系统、NavMesh、寻路
- 大型粒子系统
- Shader Graph / 材质图
- 资源商店 / 插件市场
- 多窗口编辑器 / 协同编辑
- 完整全局光照 / 生产级路径追踪
- 完整刚体仿真 / 关节 / CCD / 布娃娃（0.2 只做动作游戏所需物理）
- 联机/多人动作玩法
- 主机平台认证

> 0.3 和 0.4 再按目标游戏类型逐步解锁。

## 4. 总体里程碑

按 **AI 并行生成 + 1～2 名人工集成/评审 + 0.5 名设计/QA** 估算，节假日未扣除。AI 可以并行编码，但合并、测试、验收和产品判断仍需人工；排期由集成带宽决定。

| 阶段 | 时间窗口 | 版本 | 里程碑 |
|---|---|---|---|
| Phase 0 | 2026-11-02 ～ 2026-11-13 | — | 立项完成：能力清单、演示工程、基线、ADR、CI 计划 |
| Phase 1 | 2026-11-16 ～ 2027-02-07 | `0.2.0` | 可玩垂直切片 + Player 导出 |
| Phase 2 | 2027-02-08 ～ 2027-05-16 | `0.3.0` | 编辑器工具链闭环 + 物理/动画增强 |
| Phase 3 | 2027-05-17 ～ 2027-09-05 | `0.4.0 / 1.0` | 平台、网络、生态、稳定性 |

### 4.1 关键路径

```text
目标游戏定义
   ↓
资产管线（glTF + 资产数据库）
   ↓
骨骼动画 + 渲染（PBR/阴影）
   ↓
音频 + 玩法组件
   ↓
Player 导出 + 能力演示工程
   ↓
编辑器工具链（Prefab/动画/构建/Profiler）
   ↓
平台与生态
```

**关键路径上的任何一项延期，0.2.0 都会延期。** 其中资产管线、骨骼动画、Player 导出是最高风险项。

## Phase 1：可玩的 3D 动作垂直切片（12 周，`0.2.0`）

### 目标

交付一套可组合的 **3D 动作游戏引擎能力**，并用一个 3～5 分钟的示例工程验证，要求：

- 在 Hezhou 编辑器里编辑
- 能导出独立 Player
- 在干净的 Windows 机器上运行（无需安装 Mono）
- 在 Linux 上至少能运行压缩包版本
- 有骨骼动画、战斗判定、敌人、声音、HUD、关卡流程
- Windows 与 Linux 两个 Player 构建从同一套代码产出

### 1.1 音频子系统（2～3 人周）

**新增 `engine/audio`**

- 播放/暂停/停止/循环
- 音量、静音、总线
- 2D 音效 + 3D 衰减
- 流式/预加载两种模式
- C# API + 编辑器音频预览
- 打包时自动收集音频资源

**验收**

- [ ] 示例工程有背景音乐 + 至少 5 个音效
- [ ] 3D 音效随相机距离衰减
- [ ] 无音频设备时不崩溃
- [ ] 音频资源随 Player 导出

**建议技术选型**：`kira`（混音/空间音频）或 `cpal + 自研混音`；Phase 0 做 2 天 spike 后定 ADR。

### 1.2 资产管线 v2（4～5 人周）

**新增 `engine/asset`**

- 资产数据库：UUID、路径、类型、依赖、导入设置
- `.meta` 文件
- glTF/GLB 导入：Mesh、Material、Texture、Skeleton、Animation
- 纹理导入：PNG/JPEG，sRGB/线性、mipmap、压缩策略
- 资源引用从“字符串路径”升级为“AssetId”
- 资产 cooker：把编辑器资产烘焙成 Player 格式
- 资产热重载（编辑器内）

**验收**

- [ ] 导入一个带骨骼和动画的 glTF 角色
- [ ] 修改纹理后编辑器可热重载
- [ ] 工程移动目录后引用不丢失
- [ ] Player 包只包含被引用的资源

### 1.3 骨骼动画（4～5 人周）

- glTF skin/joint 导入
- GPU 蒙皮（顶点着色器）
- AnimationClip 播放/循环/速度
- 动作状态机：Idle / Run / Jump / Attack1 / Attack2 / Hit / Death
- 动作交叉淡入淡出、攻击连段窗口
- 动画事件（脚步、攻击命中帧、受击帧）
- 根运动（0.2 可选；动作位移优先由控制器驱动）

**验收**

- [ ] 角色可播放 Idle/Run/Jump/Attack1/Attack2/Hit/Death
- [ ] 轻攻击两段连招可衔接
- [ ] 状态切换无明显跳变或滑步
- [ ] 骨骼动画在 Windows/Linux Player 中均正常
- [ ] 动画资源随包导出

### 1.4 渲染：PBR + 阴影 + 后处理（4～5 人周）

- PBR 材质：albedo / metallic / roughness / normal / AO
- 方向光 Shadow Map（至少 1 级，建议 2～3 级 cascade）
- Tone mapping + Gamma
- Bloom（可选，若示例工程需要）
- 保留 FXAA
- 渲染管线可配置（低/中/高）

**验收**

- [ ] 基准场景有可见阴影
- [ ] 金属/粗糙度视觉正确
- [ ] 1080p 下样例场景达到 60 FPS（目标硬件见 §8）
- [ ] 低配模式可关闭阴影/Bloom

### 1.5 Player 导出（4～5 人周）

**新增 `engine/player`（或 `examples/src/hezhou_player.rs` + 构建器）**

- `hezhou build` 或编辑器“导出游戏”
- 输出：可执行文件 + 烘焙资产 + 预编译 C# 程序集 + 运行时
- **Windows Player**：无终端、无 Mono 依赖、可打包 zip
- **Linux Player**：可执行 + 资产目录/压缩包，不依赖系统 Mono
- 启动参数：窗口模式、分辨率、日志路径
- 构建配置：启动场景、窗口标题/图标、版本号
- 跨平台约束：资产逻辑路径、大小写规范化、路径分隔符抽象、字体随包、输入映射一致
- 跨平台兼容清单：路径/大小写、可执行权限、动态库、Vulkan 驱动、日志目录、换行符
- CI：Windows + Ubuntu 双平台构建同一个 commit，产物必须可启动

**验收**

- [ ] 干净 Windows 机器双击即可运行示例工程
- [ ] 干净 Linux 机器解压即可运行示例工程
- [ ] 两个平台都不要求用户安装 Mono
- [ ] 两个平台都不弹出终端
- [ ] 构建产物可重复、带版本号
- [ ] 构建日志和错误信息可读
- [ ] 同一份工程/资产在 Windows 和 Linux 上表现一致

### 1.6 Prefab 与场景工作流（2～3 人周）

- Prefab 资产：保存实体子树
- 实例化、覆盖字段、Prefab 嵌套（基础）
- 场景切换/加载
- 启动场景配置

**验收**

- [ ] 角色/敌人/道具以 Prefab 形式复用
- [ ] 修改 Prefab 后场景实例可更新
- [ ] 示例工程至少 2 个场景可切换

### 1.7 自研动作物理与角色控制（4～5 人周）

> 已确认不接 rapier。0.2 只做 3D 动作游戏真正需要的物理，不追求完整刚体仿真。

- 胶囊角色 vs 静态 Box/Sphere/Plane 的扫掠碰撞
- 固定时间步 + 渲染插值，避免帧率影响手感
- 地面吸附、台阶、斜坡、空中控制
- 碰撞层/掩码、触发器
- 攻击命中盒（胶囊/球/盒）与命中事件

## 9. 团队与协作

### 9.1 执行模型

不再按传统人头配置排期，采用 **AI 并行工作流 + 人工集成/评审**：

| 角色 | 数量 | 职责 |
|---|---|---|
| 产品/技术负责人 | 1 | 目标、范围、ADR、最终验收 |
| 人工集成/评审 | 1～2 | 合并冲突、代码审查、跨模块联调、性能/手感把关 |
| 设计/QA | 0.5 | 能力演示工程、验收、回归 |
| AI 工作流 | 6～8 并行 | 渲染、资产、动画、音频、物理、Player、编辑器工具、测试/文档 |

**AI 工作流拆分原则**

- 每个工作流有独立写作用域，避免同时修改同一核心文件
- 每个任务必须带验收标准和测试，不接受“只生成代码不验证”
- 核心接口（Scene/RenderContext/AssetId/Player 格式）先由人工写 ADR，再并行实现
- 每周至少一次人工集成窗口，防止分支长期漂移
- AI 生成量越大，测试和审查要求越高；不以“代码行数”衡量进度

### 9.2 协作节奏

- 每周一次里程碑同步（30 分钟）
- 每两周一次可运行 Demo（必须能跑）
- 每个 Phase 结束做一次回顾和范围重估
- 所有跨模块接口先写 ADR/接口草案，再并行开发

### 9.3 Issue 规范

- `P0`：阻塞 0.2.0 发布
- `P1`：影响体验，0.3.0 前必须解决
- `P2`：增强项/生态项
- 每个 issue 必须写：背景、验收标准、影响文件/模块、估算
